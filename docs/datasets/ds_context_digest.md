Пример: «BPM» + опыт Directum (СЭД) → 0.6.

Не переоценивать специфичные требования:

Если требование специфичное (embedded, SaaS, CPaaS, конкретный стек), а опыт кандидата смежный, но не идентичный — match 0.4–0.7, НЕ 1.0.

Пример: AI-рекомендательная система ≠ SaaS-продукт → 0.5.

Пример: интеграции с Банком России ≠ CPaaS → 0.3.

Жёсткий фильтр (правило 9):

Если хотя бы одно level=1 имеет match < 0.7 → suitable = false, даже если остальные 80% совпадают.

Исключение: если level=1 — «плюс» (не обязательное), а не отсекающее. Тогда фильтр не применяется.

Исключение: если level=1 — soft-требование («желательно», «будет плюсом»). Тогда match < 0.7 не блокирует.

Финальная проверка перед suitable=true (правило 12):

Перечитать все level=1.

Убедиться, что каждое имеет match ≥ 0.7.

Если есть level=1 с match < 0.7 — вернуть false с указанием причины.

Проверить, что нет приписанного опыта (НИОКР, управление ИБ-проектами, PKI, 1С:ERP, LLM/RAG, embedded, программирование, администрирование).

2.3. Отраслевой опыт — пропорция
Формула:

Прямой опыт (работал в этой отрасли): match = M/N, где M — число лет в отрасли, N — требуемое число лет. Ограничение сверху 1.0.

Смежный опыт (работал в близкой отрасли): match = (S/N) × 0.5, где S — число лет в смежной отрасли. Ограничение 0.5.

Нет опыта: match = 0.0–0.2 (в зависимости от переносимости).

Правило «один проект ≠ опыт в отрасли»:

Один проект в отрасли (например, X5 Retail Group для ритейла) не даёт match > 0.5, даже если проект длился 1,5 года.

Для match 0.8+ нужно 3+ года в отрасли или 2+ проекта.

Пример: «Опыт в ритейле от 5 лет» + один проект X5 (1,5 года) → match 0.3, не 0.8.

Пример: «Опыт в госсекторе от 5 лет» + ГАС «Выборы» (2,7 года) + ЭЛАР/Роспатент (1 год) + Инфосистемы Джет (Минобороны) → 4+ года, match 0.8.

Примеры:

Требуется 5 лет в HoReCa. У кандидата 0 лет в HoReCa, но 5 лет в ритейле (X5) — смежно. match = (5/5) × 0.5 = 0.5 → не отсекающий, но снижает.

Требуется 3 года в FinTech (PSP/EMI). У кандидата 2 года интеграций с Банком России — смежно. match = (2/3) × 0.5 = 0.33 → слабо.

Требуется 5 лет в госсекторе. У кандидата 2,7 года в ГАС «Выборы» + 1 год в ЭЛАР (Роспатент) = 3,7 года — прямой. match = 3.7/5 = 0.74.

Требуется 3 года в банке. У кандидата 0 лет в банке, есть интеграции с Банком России — смежно. match = (2/3) × 0.5 = 0.33.

Требуется 2 года в страховании. У кандидата 0 лет в страховании, нет смежного. match = 0.0.

2.4. Переносимые роли (роль ≠ функция)
Принцип: название роли ≠ суть функции. Оцениваем по функции, а не по названию.

Примеры:

Delivery Manager ≠ Project Manager. DM — фасилитация, коучинг команд, Agile-метрики, процессы. PM — сроки, бюджет, результат. У кандидата PM-профиль. Если вакансия требует именно DM (фасилитация, коучинг) — match 0.3–0.5, не 1.0.

Product Manager ≠ Project Manager. PdM — продуктовые метрики, roadmap, A/B, unit-экономика, Data Catalog. PM — проекты, сроки. У кандидата есть продуктовый опыт (Созвездие, Frontier), но не в чистом виде. match 0.5–0.7.

Scrum Master ≠ Project Manager. SM — коучинг, фасилитация, Agile-церемонии, метрики команд. PM — управление. match 0.3–0.4.

Chief of Staff ≠ PM. COS — P&L, unit-экономика, матричное управление без власти, аудит планов. match 0.4–0.6.

Аккаунт-менеджер ≠ PM. Аккаунтинг — развитие B2B-партнёров, коммерческие показатели, гео. match 0.2–0.4.

Партнёрский менеджер ≠ PM. Партнёрства — поиск поставщиков, закупки, договоры. match 0.4–0.6.

Администратор проектов ≠ PM. Администратор — младшая роль, документация, поддержка PM. Кандидат overqualified. match 0.2–0.4.

Координатор ≠ PM. Координатор — младшая роль, координация. Кандидат overqualified. match 0.2–0.4.

Руководитель направления ≠ PM. Может быть техническим лидером, а не PM. Оценивать по функциям: управление людьми, бюджет, процессы, техническая экспертиза. match 0.6–0.9 в зависимости от требований.

Руководитель департамента ≠ PM. Топ-роль, стратегия, бюджеты, реструктуризация. match 0.6–0.8, если есть управленческий опыт.

Правило: если функция не совпадает — снижать match по ключевой группе, даже если название похоже.

2.6. Дублирование в отсечках («сумма равных»)
Правило: если требование повторяется в разных формулировках (например, «опыт в банке» и «опыт в финансовой сфере»; «опыт в рознице» и «опыт в HoReCa») — оценивать по жёсткой формулировке. Не суммировать, не усреднять в пользу кандидата.

Пример: «Опыт в рознице, HoReCa или FMCG». У кандидата есть ритейл (X5), но не розница в чистом виде и не HoReCa. match 0.4–0.5, не 1.0.

2.8. Связки требований (21a, 21b, 21c)
21a. Связка (2–3 пункта, следующий уточняет предыдущий) — match = MIN.

Если требование состоит из нескольких связанных пунктов, где каждый следующий уточняет предыдущий — match = MIN из всех.

Пример: «Опыт управления IT-проектами от 3 лет, в том числе в области embedded-систем» → match = MIN(1.0 PM, 0.6 embedded) = 0.6.

Пример: «Опыт PM от 5 лет, включая 2+ года в роли РП на проектах внедрения» → match = MIN(1.0, 0.9) = 0.9.

Пример: «Опыт в банке или FinTech от 3 лет, включая опыт с РКО» → match = MIN(0.3, 0.1) = 0.1.

21b. Список однотипных требований — match = MAX.

Если требование перечисляет однотипные варианты («X или Y или Z») — match = MAX из всех.

Пример: «Опыт с Jira, Confluence или аналогами» → MAX(1.0 Jira, 1.0 Confluence) = 1.0.

Пример: «Опыт в банке, FinTech или страховании» → MAX(0.2 банк, 0.3 FinTech, 0.0 страхование) = 0.3.

Пример: «Опыт с 1С, SAP или аналогами ERP» → MAX(0.2 1С, 0.3 SAP, 0.7 ERP) = 0.7.

21c. Условия через «если» — match зависит от условия.

Если требование сформулировано как «если X, то Y» — оценивать по Y при наличии X.

Пример: «Если опыт в банке — обязательно РКО» → при отсутствии банка match по РКО не применяется, но match по банку = 0.2.

Пример: «Если опыт с 1С — знание конфигураций» → при отсутствии 1С match по конфигурациям не применяется, но match по 1С = 0.2.

Пример: «Опыт PM, если есть — опыт в Agile» → match по Agile = 1.0, match по PM = 1.0.

Правило: связки и списки — самые частые источники ошибок. Проверять перед финальным вердиктом.

ЧАСТЬ 3. НАКОПЛЕННЫЕ НЮАНСЫ (критичные, не входящие в стандартные правила)
Локация не Москва без переезда — отсекающий. Кандидат в Москве, не готов к переезду, только редкие командировки. Если вакансия в Ижевске, Ростове, Новокузнецке, СПб (постоянно) — reject. Если командировки 1–2 раза в месяц — borderline. Пример: ИЦ ИАС (Новокузнецк) — reject, несмотря на 95% по компетенциям.

      "evidence": "цитата из профиля (до 40 символов, 2-5 ключевых слов)"
    }
  ],
  "verdict": "Подаваться/Не подаваться. Соответствие X%. Сильные: ... Слабые: ...",
  "confidence": 0.0-1.0
}
Обязательные поля:

suitable (bool) — итоговый вердикт.

requirements (list) — список требований, каждое с level, label, text, match, evidence.

verdict (str) — краткое обоснование (до 250 символов), без «уровень N».

confidence (float) — уверенность в оценке (0.0–1.0). Не заполнять, если система считает сама.

Правила заполнения:

level=1 — отсекающие требования (опыт от N лет, высшее образование, обязательное наличие X, локация не Москва без удалёнки, отраслевой опыт как обязательный, ключевые технологии).

level=2..7 — остальные требования, сгруппированные по смыслу. Уровни 2–4 — самые важные, 5–7 — менее.

label — название уровня (одинаковый для всех элементов уровня, для группировки).

match — 0.0 (нет соответствия) … 1.0 (полное). Промежуточные значения — норма (0.2, 0.4, 0.6, 0.8).

evidence — короткая цитата из профиля (до 40 символов, 2–5 ключевых слов). Если match ≥ 0.4, но прямой цитаты нет — ближайший релевантный факт. Пустое evidence — только при match ≤ 0.2.

verdict — «Подаваться/Не подаваться. Соответствие X%. Сильные: ... Слабые: ...». Для отказов начинать с причины. Не добавлять «уровень N».

confidence — 0.0–1.0. Высокая (0.85–1.0) — когда вердикт однозначен. Средняя (0.6–0.84) — когда есть смежные факторы. Низкая (0.3–0.59) — когда оценка спорная.

Правила интерпретации:

Требование «опыт в X или Y» — ОДИН элемент с максимумом из двух матчей (21b).

Связка «X, в том числе Y» — MIN из всех (21a).

Условия через «если» — match зависит от условия (21c).

Отрицания («НЕ должно быть X», «без опыта в X») — инвертированное требование: match = 1.0, если X нет; match = 0.0, если X есть.

Не выдумывать требования, которых нет в вакансии.

Не приписывать опыт, которого нет (НИОКР, управление ИБ-проектами, PKI, 1С:ERP, LLM/RAG, embedded, программирование, администрирование).

Финальная проверка: все level=1 имеют match ≥ 0.7? Если нет — suitable=false.
