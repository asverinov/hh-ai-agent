# INTERACTION — правила общения с Пользователем

**Назначение:** чтобы каждая новая сессия Агента не переспрашивала одно и то же.
Читать в начале сессии вместе с ARCHITECTURE.md и TECH_DEBT.md.

**Кто есть кто:**
- **Пользователь** — не программист. Владелец проекта, принимает бизнес-решения.
- **Агент** (эта сессия) — код, тесты, инфраструктура, документация.
- **Эксперт** (отдельная сессия) — контент: промпты, правила фильтрации, архитектура оценки, аудит результатов.

---

## 1. Формат команд терминала

**Один `printf '\n\n\n\n'` в начале блока команд.** Не перед каждой командой.
Пользователь копирует весь блок целиком и видит, где конец вывода, где начало.

Если команд несколько и между ними нет логики, которую должен выполнить
Пользователь, — давать единым блоком с `echo "=== N. ... ==="` подписями.
Пользователь по подписям понимает, где чей вывод.

**Diff-блоки и патчи — только для просмотра, не выполнять.** Оформлять
обычным текстом (не в bash-блоке) с явной пометкой «только для просмотра,
не выполнять». Иначе Пользователь случайно запускает diff в терминал.

**Пример правильного блока:**

    printf '\n\n\n\n'
    cd ~/hh-ai-agent
    source venv/bin/activate
    echo "=== 1. Что делаем ==="; команда1
    echo "=== 2. Что делаем ==="; команда2

**Пример неправильного (не делать):**

    printf '\n\n\n\n'; echo "=== 1 ==="; команда1
    printf '\n\n\n\n'; echo "=== 2 ==="; команда2   ← лишние printf

## 2. Бекапы

**Всегда в `<каталог>/bak/<файл>.bak-<timestamp>`**, не inline рядом с оригиналом.

    mkdir -p bak
    cp file.py bak/file.py.bak-$(date +%Y%m%d_%H%M)

Для скриптов в `scripts/` — `scripts/bak/`. Для `docs/` — `docs/bak/`.
Не `file.py.bak` рядом с `file.py` (замусоривает рабочую папку, попадает в git status).

**Перед разрушительными операциями (массовый UPDATE, миграция БД) — бэкап `agent.db`:**

    cp agent.db bak/agent.db.bak-<причина>-$(date +%Y%m%d_%H%M%S)

---

## 3. Контентные файлы — не в git

Файлы с личными данными (`profile.yaml`, `prefilter_rules.yaml`, `resume_*.txt`,
`assess1.md`/`assess2.md` с наполнением) — **не коммитить**. В `.gitignore`.
В git — только шаблоны (`*.example.yaml`) и код.

Пользователь сам кладёт контентные файлы в виртуалку. Если файла нет — сказать,
не создавать.

---

## 4. Не перегружать сессию файлами

Когда присылаешь результат — **Markdown-отчёт** (читаемый), не полный JSONL.
JSONL — только по запросу, конкретные id (`grep '<id>' reports/*.jsonl`).
Логи терминала — последние 50–100 строк + `=== ИТОГ ===`.

Если нужен полный файл для аудита — сказать явно «нужен полный X, потому что Y».

---

## 5. Проверять факты, не полагаться на дайджесты

Дайджесты (AI5–AI9) могут содержать устаревшие утверждения (например, «прод на v1.4»,
когда реально был на старой архитектуре). **Всегда** проверять по коду и гиту:
`grep -n`, `git log -S`, `git show`.

Если утверждение из дайджеста расходится с кодом — сказать об этом, не
повторять ошибку.

---

## 6. Останавливать всё по команде

Пользователь может сказать «стоп всё». Команда:

    pkill -TERM -f "hh-ai-agent"
    sleep 3
    pkill -KILL -f "hh-ai-agent"
    pgrep -af "hh-ai-agent"   # проверить, что пусто

**После «стоп» — никаких фоновых запусков** (`nohup`, `&`, редиректы в `/tmp/*.log`)
до отдельного «поехали». Всё foreground, с выводом в терминал.

Долгие процессы (миграция, бэкфилл) — `foreground` (Пользователь смотрит) или
`tmux`/`nohup` с явным подтверждением и логом, который Пользователь может
`tail -f`.

---

## 7. Язык и объяснения

Пользователь не программист. Если объясняешь техническое — на пальцах, с
аналогиями. Не «anchor не совпал из-за trailing space», а «в файле лишний
пробел в конце строки, поэтому замена не сработала — файл не изменён».

Разделять «что сломано» / «что делать» / «что будет, если не делать».
Без жаргона, где можно.

---

## 8. Роли: Агент и Эксперт

**Агент:** код, тесты, инфраструктура, документация, запуск процессов.
**Эксперт:** промпты (`assess1.md`, `assess2.md`, `ds_cover_letter_digest.md`),
правила фильтрации (списки excluded, пороги), архитектура оценки (precision vs
recall), аудит результатов.

Если правка затрагивает **контент** (что писать в промпте) — к Эксперту.
Если **код** (как читать/писать) — Агент. Если **и то, и другое** — сначала
Эксперт решает «что», Агент реализует «как».

Главы контентных файлов Эксперт передаёт через Пользователя. Агент не создаёт
и не правит контентные файлы сам — Пользователь вставляет, Агент проверяет
реализацию.

---

## 9. Формат ответа Пользователю

- **Сначала — что сделано / что сломано**, потом детали.
- **Команды — в ```bash```-блоках**, с `printf '\n\n\n\n'` в начале.
- **Diff/патчи — в обычном тексте**, с пометкой «только для просмотра».
- **Результаты** — что ожидали / что получили / что дальше.
- Если запутался или не уверен — сказать прямо, не выдумывать.


## 10. Запуск воркеров — отдельный терминал с живым выводом

Каждый воркер (`browser_worker`, `assess_worker`, `search_worker`, `run_tg_bot`, `migrate_assess` и др.) запускается в **отдельном терминале**, с непрерывным выводом на экран.

**Формат:**

    DISPLAY=:99 PYTHONPATH=. python3 -u scripts/<worker>.py 2>&1 | tee /tmp/<worker>.log

- `-u` — unbuffered: Python сразу пишет в stdout, а не копит в буфере.
- `2>&1 | tee /tmp/...` — stderr туда же + дублирование в файл. Лог остаётся для `grep` / `tail` после закрытия терминала.

**Почему:**
- Пользователь не программист. Видеть, на каком шаге воркер — единственный способ отличить «работает» от «завис».
- При зависании последняя строка лога (обычно `pw:api ... waiting for locator(...)` или `INFO ...`) сразу показывает, где стоп.

**Чего не делать:**
- Не использовать `nohup ... &` без `tee` для отладки и первых прогонов.
- Не запускать несколько воркеров в одном терминале (перепутается вывод).
- Не трогать VNC, пока работает `browser_worker` (ручные клики + скрипт = «псевдографика» в поле сопровода, сломанный submit).

**Остановка:** `Ctrl+C` в том же терминале. Если не срабатывает — `pkill -TERM -f "scripts/<worker>.py"`, через 3 сек `pkill -KILL`.
